# Reverse-Engineering Fan Calculators into Game Rules

Fan calculators were built to predict the live server, so their code *is* the community's best model of the server's formulas. Treat them as executable specifications.

## Procedure

1. **Gather every version** of each tool. Diffing versions shows which rule changed in which game patch. Keep each in `calcs/raw/<host>/<tool><ver>/`.
2. **Map the code:** run `scripts/js_inventory.py <dir> > inventory.md`. This lists functions, formula lines, data tables and version comments.
3. **Find the entry point.** Look at the HTML for the `onclick` or `onsubmit` handler and follow it into the compute function.
4. **Extract formulas verbatim**, with file and line references. Write them in pseudocode and keep the original constants. Note when rounding happens: `floor` at each step and `floor` at the end give different results.
5. **Extract data tables to JSON:** ships, weapons, equipment, races, drones, stations. Write one file per table per version, for example `data/<tool><ver>_<table>.json`, generated by a small script rather than typed by hand.
6. **Run the original code headless.** Copy `templates/headless_harness.js`, keep the original files unmodified, stub the DOM, seed `Math.random`, and run many trials. This creates golden outputs.
7. **Prove equivalence.** The new engine must match the harness:
   - exactly, for deterministic functions such as ship cost, ratings and turn costs;
   - statistically, for random combat: mean and percentile damage, time-to-kill and win rate over thousands of seeded trials, within a stated tolerance.
8. **Reconcile with official text.** Where the calculator disagrees with the official help or changelog for the same version, the official source wins for that version. Record the difference in a conflicts table.

## Typical outputs

- `mechanics/combat_engine.md`: turn order, hit or evade chance, damage, criticals, shields and armor, drones, special cases, all with line citations.
- `mechanics/ship_building.md`: hull stats, upgrade cost curves, level and rating formulas, equipment rules.
- `mechanics/world_economy.md`: visibility, ports and pricing, goods, stations and the map.
- `mechanics/data/*.json` and `mechanics/harness/*.js`.

## Running many sources in parallel

Split the work by tool family (for example combat simulator versions; ship builders; visibility, ports and stations). Give each subagent:
- absolute paths to its raw files and the output path;
- the requirement to cite file and line for every formula;
- a version-conflicts table;
- a working harness or a statement of why one isn't possible.

Afterwards, spot-check that the harness runs (`node harness/*.js`) and that a few cited lines exist.

## Pitfalls

- Header comments can lie. A file named 2.2 may say "LemmySim 2.1" inside, so record both.
- Calculators can mix rules from several versions. A tool built after a rollback patch may keep removed items.
- `Math.random` in the originals: always seed it in the harness, or comparisons can't be reproduced.
- Old JS quirks: `document.all`, `eval` of strings built from form inputs, globals declared without `var`, and numeric strings concatenated instead of added. Stub these as needed, but don't "fix" the originals.
