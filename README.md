# Custom Skills

**The portable skill and persona package for Hermes Agent.**

A library of agent skills with a machine catalog and a router, built and
gated by David Patton. A snapshot of the methods, gates, and personas he
runs, in one repo a fresh install (or another harness) can rebuild itself
from. It is a snapshot, not a live sync: the private source repo moves
first, and this package is republished from it.

## Start here

This is the consumer front door. If you only want to use the library,
this section is the whole job: get a pinned copy, read the three files
that run the show, and let the catalog route your tasks.

The registry holds 304 records covering 251 canonical units (skills
and personas, with duplicate and local variant records counted
separately in the total). The catalog is generated from the tree
itself, so it cannot drift away from what is actually in the repo.

### Get a copy: pin the tag

Do not track a moving branch. Pin a snapshot tag.

1. Clone the public mirror:

   ```bash
   git clone https://github.com/David2024patton/custom-skills-public
   cd custom-skills-public
   ```

2. List the snapshot tags and check out the newest one:

   ```bash
   git tag -l "snapshot-*"
   git checkout <newest snapshot tag>
   ```

   No git? Download the ZIP for that same tag from the repo releases
   and tags page instead, and unpack that.

3. Make your copy private. If you push your copy anywhere, push it to
   a private repo of your own. Part of this library is not cleared for
   redistribution (see Licensing below), and presence in this repo is
   not permission.

### The three files that run the show

| File | What it does |
|---|---|
| `registry.json` | The catalog. Every skill has a canonical ID, trigger keywords and aliases, a checksum of its SKILL.md, and a risk class. Machine generated by `scripts/build-registry.py`; never hand edited. |
| `collection-router/` | The router skill. It reads the registry and picks which skill fits a task, instead of you guessing or loading everything. |
| `THIRD-PARTY.md` | The licensing map. Read this before reusing anything. It is the source of truth for who owns each skill and what may be done with it. |

### How an agent or MCP server consumes the catalog

1. Load `registry.json` in your server or agent setup.
2. Match the task to a skill by its triggers and aliases.
3. Respect the risk class. Skills classed destructive, money, or
   external send need a confirmation step before they run, the same
   way a write tool needs one. A record whose risk source is the
   registry default is unclassified: treat it as confirmation required
   before any action beyond reading.
4. Load that skill's SKILL.md from the path the registry record gives
   you, and follow it.
5. Check the checksum. Each record carries a SHA-256 checksum of its
   SKILL.md. If you edit a skill, its checksum stops matching the
   registry. That is by design. Regenerate the registry with
   `scripts/build-registry.py` rather than editing it by hand.

One limit, stated plainly: only one skill in this repo is mapped for
MCP use (see MCP below). Everything else is agent instructions,
SKILL.md playbooks for an agent with tools, not MCP tools, and must
not be served as MCP tools without a mapping of its own.

### The Critic family

`personas/critic/` plus the five lenses under
`skills/software-development/critic-lens-*` (code, claims, compliance,
growth, ux) are the review gate this library was shipped through:
three independent critics in parallel, findings sorted unanimous,
majority, and lone wolf, and a one line verdict of ship, fix first,
or do not trust. Run it on your own work before you ship. It is how
this repo got to clean.

## About the library

Skills come from everywhere: written by David, built by whichever AI
he is working with, or picked up from other projects and kept because
they work. This repo is the one home for all of them, no matter where
they started.

Each skill is self-contained in its own folder:

| Piece | Role |
|---|---|
| `SKILL.md` | the method, written so an agent can run the task cold |
| `skill.yaml` | name, title, and the one-line description, in the folders that carry one |
| `references/`, `scripts/`, `templates/` | supporting material where a skill needs it |

Not every skill carries a `skill.yaml`: 110 of the 281 skills in this
repo carry a `skill.yaml` (recount 2026-10-27). The rest state their
name, author, and license in the `SKILL.md` frontmatter alone, or
carry no frontmatter at all; [THIRD-PARTY.md](THIRD-PARTY.md) records
which is which for every skill.

## The persona pipeline

This repo carries the portable pieces of the Hermes persona pipeline,
so another harness or a fresh Hermes install can rebuild the whole
system from here: phase profiles that hand work down a parent-chained
kanban line, a critic stack that attacks every diff before it ships,
and the QA law that decides what done means.

## Publishing

A redacted snapshot publishes to the
[public mirror](https://github.com/David2024patton/custom-skills-public)
with one command from the private repo:

```bash
bash scripts/publish-public-mirror.sh
```

What the publish gate actually does, stated plainly: a maintained
blocked list of known private values is stripped and scanned for,
pattern scans look for credential and identifier shapes, and gitleaks
scans the staged tree against a documented baseline. Content the
blocked list names is dropped first, and index files are pruned of
stale lines. That is a maintained list plus scanners, not a
guarantee: an identifier that is not on the list and does not match a
scanned shape can pass, which is why any file new to a snapshot also
gets a human read before it publishes. The redaction map and the
scope list live only in the private repo's `scripts/` and never enter
a snapshot.

snapshot tag, do not track a moving branch.
